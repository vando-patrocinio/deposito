## 2. OS 4 SISTEMAS DE AUTORIZAÇÃO COEXISTINDO

Esta é a raiz do comportamento imprevisível.

| # | Sistema | Fonte da verdade | Onde decide |
|---|---|---|---|
| **1** | **role legado** | `users.role` ∈ {colaborador, gestor, financeiro, administrador, auditor, atendimento, tecnico, gestor_rede} | 937 `require_role()` + 82 `user.role==` em handlers |
| **2** | **access_tags** | `users.access_tags: [str]` | `require_tag()` (0 callers) + `effective_tags(user)` em `auth.py:_user_public` |
| **3** | **access_profiles** | `users.profile_id` → `access_profiles.access_tags` | Sync espalhado em `routes/clock.py` quando colab edita |
| **4** | **is_super_admin** | `users.is_super_admin: bool` | 198 referências dispersas |

**Cada handler escolhe arbitrariamente qual dos 4 consulta.**

Exemplo concreto reproduzido hoje em PROD:
- Gestor coloca colab `JEFFERSON` no profile "Administrador" (`prof-b70fd621c4`, 60 access_tags).
- Sync **só atualizou** `users.profile_id` + `users.access_tags`.
- `users.role` continuou `colaborador`.
- `/api/propostas` (sistema #1) usa `require_role("gestor","atendimento")` → bate em `role` → **403**.
- Front exibe badge `COLABORADOR` pois lê `users.role`.
- Sintoma percebido: "mudei pra admin e não foi".

**O bug não é de uma linha. É de arquitetura.** Mudar uma fonte não propaga pras outras 3.

## 5. ONDE QUEBRA — INVENTÁRIO DE FALHAS

### A. Sincronização Colab ↔ User

**Sintoma:** "Coloquei perfil Administrador no colaborador e ele continua sem acesso."

**Quebra:**
- O cadastro de Colaborador tem `profile_id`, `cargo`, `clock_in_enabled`, etc.
- O User tem `role`, `profile_id`, `access_tags`, `is_super_admin`, `collaborator_id`.
- O vínculo entre os dois é **frágil** (3 chaves possíveis: `users.collaborator_id`, `users.email == collab.email`, `users.email == collab.mobile_access_email`).
- A propagação só atualizava `profile_id`+`access_tags`, deixando `role` legacy intocado. (Patch aplicado hoje em `routes/clock.py`, mas é remendo — o problema verdadeiro é existirem 2 entidades pra mesma pessoa.)

### B. Identidade fragmentada

**Sintoma:** "Login pelo app funciona, pelo web não" / "Funciona em uma máquina e em outra não."

**Quebra:**
- Mesmo email pode existir simultaneamente em `users`, `client_portal_users`, `fleet_portal_users`, `parcerias_partner_users`, `security_portal_users`, `collaborators.mobile_access_email`, `public_access_tokens.email`.
- Cada portal valida senha contra sua própria coleção. **Não há single source of truth.**
- Não existe noção de "pessoa" (Identity) — apenas "user-do-portal-X".

### C. Status do colaborador é inconsistente

**Sintoma:** "Desliguei o colab mas ele ainda loga."

**Quebra:**
- `collaborators.active: bool` e `collaborators.deactivated_at: datetime` coexistem (visto em DIOGO HENRIQUE: `active:true, deactivated_at:2026-05-10`).
- `users.active: bool` é **independente** do `collaborators.active`.
- Desativar o colab no Cadastro **não desativa o User**. Login segue funcionando.

### D. Magic links sem governança

**Sintoma:** "Link de acesso compartilhado fica funcionando pra sempre."

**Quebra:**
- 14 magic links ativos sem `expires_at` consistente.
- Não há "revogar todos os links do usuário X" na UI.
- `public_access_tokens` (4 docs) abrem porta com **role=administrador sintético** (visto em `auth.py:251`) — qualquer um com a URL vira admin sintético.

### E. Decisão de role usa nome ("administrador") como string

**Sintoma:** "Criei perfil customizado e RBAC ignora."

**Quebra:**
- 937 `require_role("administrador")` espalhados. Nome canônico em string.
- Profiles novos (`prof-XXXX`) são **invisíveis** pro `require_role` — não importa quantas tags tenham.
- `access_tags` foi a tentativa de resolver isso (`require_tag(...)`) — mas tem **0 callers**.

### F. RBAC middleware vs handler guard duplicam regras

**Sintoma:** "Liberei o endpoint X mas ainda dá 403."

**Quebra:**
- `rbac_policy.py::ROLE_RULES` (130 prefixos com sets de roles).
- Cada handler tem `require_role(...)` próprio.
- **As duas regras precisam concordar.** Frequentemente o middleware libera mas o handler bloqueia (ou vice-versa).
- Hoje liberei `/api/lousa/public/` no middleware mas só funcionou porque o handler **não tinha** `require_role`. Em outros endpoints similares, ainda dá 403.

### G. `is_super_admin` é flag invisível

**Sintoma:** "Vando é super admin mas alguns endpoints reclamam."

**Quebra:**
- Setado em 2 lugares: `users.is_super_admin: bool` e `access_profiles.is_super_admin_profile: bool`.
- 198 checagens dispersas. Algumas leem `users.is_super_admin`, outras `user_has_super_admin_profile(user)` (async, lento, requer DB).
- A inconsistência entre os dois flags é silenciosa.

### H. Permissões granulares **não existem**

**Sintoma:** "Quero que esse vendedor veja só clientes ATIVOS, não bloqueados."

**Quebra:**
- Não há permissão tipo `subscribers.view.active_only`. Só `subscribers` (string crua).
- `access_tags` (`subscribers`, `clientes`, etc.) são **módulos**, não permissões.
- Cumprimento da Lei (LGPD) precisaria de filtros por escopo — **inexistente**.

### I. Sessões / Single-Session foi removido

Visto em `auth.py:279-287`:
```
NOTA: removida a verificação single-session-per-user (14/05/2026).
```

**Quebra:** o JWT vive 30 dias e é **válido em qualquer dispositivo simultaneamente**, sem invalidação no `logout` (que é apenas client-side limpando localStorage). Não há revogação real.

### J. Auditoria de acessos é parcial

**Existe:**
- `login_attempts` (rate-limit)
- `payroll_access_logs` (só holerite)
- `secrets_access_log` (só secrets)
- `auth_recovery_log` (só reset de senha)

**Não existe:**
- `audit_collaborators` (mudanças em colab)
- `audit_permissions` (atribuição/revogação de profile)
- `audit_login` (todo login bem-sucedido, IP, device)
- `audit_profiles` (mudanças em perfis)

## 7. DEPENDÊNCIAS OCULTAS

1. **`access_tags.effective_tags(user)`** silencia exceções e retorna fallback — qualquer divergência vira "ok" em vez de erro.
2. **`require_role` trata `administrador` e `auditor` como super-roles** (linha 302 de `auth.py`): qualquer endpoint que pede gestor também aceita auditor. **Surpresa:** auditor pode editar tudo.
3. **`OWNER_PASSWORD` no `.env`** sobrescreve a senha do Vando em **todo startup do backend**. Mudou senha pelo UI? Próximo deploy reverte.
4. **Backup `users_deleted_backup_2026_06_12`** — 112 docs deletados ontem. **Sem audit log do delete.**
5. **`record_login_attempt` / brute-force lockout** existe em `login_attempts` mas só pra login senha — magic-link e google-login não tem rate-limit.

## 8. RECOMENDAÇÃO — NOVA ARQUITETURA (proposta para ETAPA 2)

### 8.1 Entidades únicas

```
Identity              (1 pessoa)              ← coleção `identities`
  ├─ id, full_name, cpf, phone, status, created_at
  ├─ contacts: [{type: email|phone, value, verified}]
  └─ company_memberships: [{company_id, joined_at, status}]

Credential            (formas de provar quem é)  ← coleção `credentials`
  ├─ identity_id (FK)
  ├─ type: password|magic_link|google_oauth|magic_token|api_key
  ├─ value (bcrypt/token/oauth_sub), expires_at, last_used_at, revoked_at
  └─ device_info: ua, ip, fingerprint

Membership            (papel em uma empresa)     ← coleção `memberships`
  ├─ id, identity_id (FK), company_id
  ├─ profile_id (FK → access_profiles)
  ├─ permission_overrides: [{permission, allow|deny}]
  ├─ status: active|suspended|terminated
  ├─ joined_at, terminated_at
  └─ supervisor_id (FK)

AccessProfile         (papel reutilizável)        ← coleção `access_profiles` (já existe)
  ├─ id, company_id, name, color, description
  └─ permissions: [str] (granular: "tickets.view", "tickets.edit", etc.)

Session               (login efetivo, revogável)  ← coleção `sessions`
  ├─ id, identity_id, membership_id (ativa)
  ├─ jwt_jti (id único do token), issued_at, expires_at, revoked_at
  └─ device, ip, last_seen_at

AuditLog              (registro imutável)         ← coleção `audit_log`
  ├─ id, actor_identity_id, target_identity_id|None
  ├─ action (login.success, profile.assigned, etc.), at, ip, ua
  └─ before: dict, after: dict
```

### 8.2 Permissões granulares (não cargos)

```
Permission keys (proposta inicial, 80–120):
  tickets.view, tickets.create, tickets.edit, tickets.close, tickets.reopen,
  estoque.view, estoque.transfer, estoque.adjust, estoque.audit,
  financeiro.view.aging, financeiro.charge.dispatch, financeiro.refund,
  dashboard.executive, dashboard.operational, dashboard.financial,
  colaboradores.view, colaboradores.create, colaboradores.edit,
  colaboradores.deactivate, colaboradores.assign_profile,
  ... (lista completa em ETAPA 3)
```

**Decision:** `has_permission(user, "tickets.close")` — única função autorizadora. Substitui `require_role`, `require_roles`, `user.role==`, `is_super_admin`.

### 8.3 Migration plan (alto nível)

1. **Não deletar nada.** Coleções legadas viram read-only.
2. **Script `migrate_to_identity_v1.py`**:
   - Para cada `users` doc: cria `Identity` + `Credential(password)` + `Membership(company, role→profile)`.
   - Para cada `collaborators` doc: merge no Identity pelo CPF/email.
   - Cada portal (`*_portal_users`) vira `Credential(type=portal_X)` da mesma Identity.
3. **Compat shim** durante 30 dias: `require_role("gestor")` continua funcionando lendo do `Membership.profile.legacy_role_mapping`.
4. **Feature flag** `USE_NEW_IAM=1` permite rollback instantâneo.
